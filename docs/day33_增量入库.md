## 1. 目标

让用户在页面上传一个文档，系统解析入库，**上传完立刻能针对它提问**。

---

## 2. 实现

| 文件 | 内容 |
|---|---|
| `src/ingest.py` | 单文件入库：提取 → 切块 → 向量化 → 写入 |
| `app.py` | 侧边栏加上传组件 |

### 四步链路

```
上传字节
  ↓ ① extract_text()   PDF 用 pypdf，txt/md 直接 decode
纯文本
  ↓ ② split_into_chunks()   chunk_size=400 / overlap=80
块列表
  ↓ ③ embed_texts()     批量向量化
向量列表
  ↓ ④ 先 delete 再 add
写入 Chroma
```

---

## 3. 关键设计：覆盖式更新

```
python
try:
    col.delete(where={"source": filename})
except Exception:
    pass          # 首次上传时没有旧块

col.add(ids=..., documents=..., embeddings=..., metadatas=...)
```

**为什么必须删旧块**：
不删的话，用户重复上传同一份 PDF，库里会有两份重复内容 →
检索时重复召回同一段 → 浪费 token，还可能让模型重复回答。

**验证方式**：重复上传同一文件后，`list_documents` 的文档数不应该变多。

---

## 4. 三个边界处理

| 情况 | 处理 |
|---|---|
| 扫描件 PDF（图片型） | `pypdf` 提取为空字符串 → 抛 `ValueError("没有提取到文字…需要 OCR")` |
| 不支持的格式 | 抛 `ValueError`，界面上用 `st.warning` 而不是 `st.error` |
| 向量数 ≠ 块数 | 抛异常，防止内容与向量错配 |

**为什么扫描件要单独提示**：不判断的话用户看到"入库 0 块"却不知道为什么，
会以为是 bug。

## 6. 踩过的坑

| 现象 | 原因 | 解 |
|---|---|---|
| 上传后搜不到 | 写入的 collection 和检索的 collection 不是同一个 | 统一用 `COLLECTION_NAME` 常量 |
| 重复上传块数翻倍 | 没做 delete 前置 | 加 `col.delete(where={"source": filename})` |
| 拿不到文件字节 | 用错 API | 用 `uploaded.getvalue()`，不是 `.read()` |

> 第一个坑在 Day 23 已经踩过一次（`rag_notes` vs `rag_notes_v2`），
> 这次靠"统一常量 + 上传后立刻验证"避开了。

## 7. 面试点

| 问题 | 骨架 |
|---|---|
| 文档上传后怎么变成可检索的？ | 提取文字 → 分块（400/80）→ embedding → 写向量库；**写入前按 source 删旧块，实现覆盖式更新** |
| 上传环节有什么坑？ | ① 扫描件无文字层 ② 重复上传产生重复内容 ③ 入库与检索的集合不一致（踩过） |

---

## 8. 已知局限

- 只支持 pdf / txt / md；docx、图片（需 OCR）不支持
- 大文件（>10MB）没有进度条，用户只能等
- 入库是同步的，几十页 PDF 会让页面卡住数十秒
- 无权限控制：任何人上传的内容都进同一个库
