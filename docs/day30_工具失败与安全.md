# 工具失败处理与安全边界

## 五种场景结果
| 场景 | 结果 | 结论 |
|---|---|---|
| 工具内部抛异常 | **agent 崩溃** | 框架不兜异常，工具必须自己 try/except |
| 慢工具（3s） | 4991ms，无超时 | 缺超时机制 |
| 参数为空 | 模型正确转述 + 提示重试 | 错误信息写"怎么办"有效 |
| 正常工具 | 正常 | 基线 |
| 危险工具未确认 | 拦截成功，模型未绕过 | 二次确认有效 |

## 关键结论
1. **LangChain v1 的 create_agent 不捕获工具异常** —— 实测直接崩溃。
   这意味着：一个漏写 try/except 的新工具就能让整个 agent 不可用。
2. 需要两层防护：工具内部 try/except + agent 外层兜底。
3. 错误信息必须写"为什么错 + 该怎么办"，否则模型无法自救。
4. 危险工具：物理隔离（单独文件、不默认挂载）+ 二次确认。
   **但二次确认不能当唯一防线** —— 换模型/注入都可能绕过。
   生产环境应按角色挂不同工具集，面向用户的 agent 拿不到危险工具。

## 已知缺口
- 工具无超时机制，慢工具会拖死整个请求
