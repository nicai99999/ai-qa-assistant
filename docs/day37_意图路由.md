## 1. 目标

解决"所有问题都走 RAG"造成的浪费和误判：

| 你问 | 之前 | 之后 |
|---|---|---|
| 「你好」 | 检索 150ms → 召回无关块 → 被证据校验拒答 | 直接回应，**不检索** |
| 「我叫什么」 | 检索 → 库里没有 → **被拒答** | 读对话记忆回答 |
| 「RAG 的完整链路」 | 检索 → 校验 → 生成 | 不变 |

**注意第二行**：这是 D2 引入证据校验后的副作用——
校验不知道"这个问题该读记忆，不该查库"。

## 2. 实现

| 文件 | 内容 |
|---|---|
| `data/route_set.json` | 18 条评测集（含 3 条难例） |
| `src/router.py` | 规则分类 + 可选 LLM 兜底 + 默认降级 |
| `src/streaming.py` | 路由必须在检索之前，三分支分流 |
| `scripts/experiments/try_route.py` | 测准确率 |
| `tests/test_router.py` | 6 个用例（4 个自己写） |

### 三类意图与路径

```
输入
 ↓ 路由（规则优先，0 成本）
 ├─ chitchat  → 直接生成（不检索）
 ├─ personal  → 读记忆生成（不检索）
 └─ knowledge → 改写 → 检索 → 证据校验 → 生成
```

### 降级链

```
规则命中 → 用规则结果
规则认不出 → （可选）LLM 分类，只对 ≤12 字的短句
LLM 失败/未开启 → 默认 knowledge
```

**兜底选 knowledge 是刻意的**：把知识问题误判成闲聊 = 答错；
把闲聊误判成知识 = 慢一点但还能答对。**默认走损失小的方向。**

## 4. 关键设计决策

### 路由必须在检索之前

```
python
route = classify(question, ...)     # 先分类
...
hits = retrieve(rewritten, ...)     # 后检索
```

**反过来的话，"你好"照样会检索一遍，分流就没意义了。**
验证方法：问「你好」，看终端有没有 `检索 collection=rag_notes_v2` 那一行。

### `QUESTION_MARKERS` 里故意不放「吗」

因为「在吗」是典型闲聊。把「吗」当疑问词，「在吗」就会被判成知识问题。
**判断"是不是真在问问题"要看实质疑问词（什么/怎么/为什么），不是标点。**

### 为什么规则只到 83% 就够

规则的价值是"0 成本处理掉大多数"。剩下的有两条路：
1. 上 LLM 分类（每次多一次调用，约 300ms）
2. 接受 83%

**要看那 17% 里是什么**：如果全是闲聊，损失很小；如果有知识问题被误判，就要上 LLM。

---

## 5. 三个原则

1. **分流比优化单条链路更有效** —— 问题不该进 RAG 时，优化 RAG 没用
2. **规则兜底 + 模型增强 = 降级设计** —— 认不出时必须有个安全默认
3. **误判方向代价不对称** —— 知识→闲聊是答错，闲聊→知识只是慢，指标要分开算

---

## 6. 踩过的坑

| 现象 | 原因 | 修法 |
|---|---|---|
| 准确率 100% | 评测集没难例 | 补「本人叫X」「唠会儿天」这类 |
| 「你好」仍检索 | 分流写在检索之后 | 路由必须在 `retrieve()` 之前 |
| 「在吗」被判成知识问题 | `QUESTION_MARKERS` 里有「吗」 | 去掉「吗」和问号 |
| `AttributeError: 'NoneType'` | 对长句调了 `classify_by_rule` | 长句会返回 None，要用 `classify` |

## 7. 面试点

| 问题 | 骨架 |
|---|---|
| 为什么要意图路由？ | 不同问题的最优路径不同。「你好」不该检索，「我叫什么」该读记忆。不分类的话前者浪费 150ms、后者会被证据校验误拒 |
| 怎么分类的？ | 规则优先（个人信息关键词 + 短句问候词），认不出默认走知识路径。可选 LLM 只对短句调用，避免给每个问题加成本 |
| 为什么默认走知识路径？ | 误判代价不对称：知识→闲聊是答错，闲聊→知识只是慢。默认选损失小的方向 |
| 准确率多少？ | 规则 83%，3 条错例是刻意的难例（无特征词）。要提升需要上 LLM 分类，成本 +300ms/次 |
