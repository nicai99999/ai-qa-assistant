# 上下文管理三种策略对比

## 实验设计
- 第 1 轮埋信息：用户姓名 + 实习方向
- 中间 14 轮无关技术问答
- 第 15 轮召回测试
- 三组独立会话，各跑一遍

## 结果（含 prompt 迭代）
| 策略 | 记住 | 历史轮数 | 摘要字数 | 末轮 Prompt |
|---|---|---|---|---|
| window | ❌ | 10 | 0 | 2668 |
| summary（初版 prompt） | ❌ | 4 | 136 | 2362 |
| summary（改进 prompt） | ✅ | 4 | 146 | ~2600 |
| priority | ✅ | 9 | 0 | 2677 |

## 核心结论
1. 摘要策略的成败由一句 prompt 决定：初版丢失"用户姓名"，
   加入"必须保留姓名/身份/方向/目标"后恢复。
2. 这说明摘要压缩是「调参依赖型」方案——行为不可预测，
   同一逻辑改措辞就可能失效。
3. priority 是「规则型」方案，+9 字符换来确定性，更适合生产。
4. 最终采用三层记忆：结构化画像（不压缩）+ priority（保关键轮次）
   + 摘要（仅压缩技术问答）。

## 根因
摘要压缩的核心缺陷不是压缩率，是"模型不知道什么重要"。
正确做法是结构化记忆与非结构化摘要分离：
用户画像单独存（JSON），技术问答才进摘要。

## 选型结论
选 priority 策略 + 结构化用户画像。

推荐组合：priority（规则保底）+ 摘要（可选压缩）

理由：
1. priority 行为可预测，成本几乎为零（+9 字符）
2. 摘要能省 11% token，但可靠性依赖 prompt，适合作为"额外优化"
3. 关键信息（用户画像）应该结构化单独存，不参与任何压缩

三者分工：
  结构化存储  → 姓名、方向、偏好（JSON，永不压缩）
  priority    → 保证关键轮次不被时间挤掉
  summary     → 只在极长对话时压缩技术问答
