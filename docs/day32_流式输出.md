# 流式输出

## 三段延迟实测
| 轮次 | 检索 | 首 token | 首字延迟 | 生成总时长 |
|---|---|---|---|---|
| 第 1 次 | 720 ms | 372 ms | 1092 ms | 1140 ms |
| 第 2 次 | 301 ms | 193 ms | 494 ms | 811 ms |

## 结论
1. **首字延迟的 60-66% 花在检索上**，不是生成
2. 生成阶段首 token 只要 193-372ms，所以流式的**性能收益有限**
3. 流式的真实价值是**心理感受**：让用户知道系统在工作，而不是盯着空白
4. 首次检索比后续慢 2.4 倍（冷启动：客户端初始化 + 网络握手）

## 优化方向（未做）
- embedding / chromadb 客户端改模块级单例
- 换本地 embedding 模型可把检索降到毫秒级
- 缓存重复问题的向量

## 已知局限
- 流式下用户中途关闭页面，历史不会写入（append 在循环之后）

## 优化：客户端单例化
| 轮次 | 优化前 | 优化后 |
|---|---|---|
| 第 1 次 | 374 ms | 386 ms（冷启动无改善） |
| 第 2 次 | 174 ms | 156 ms |
| 第 3 次 | 217 ms | 138 ms |

**结论**：客户端复用连接池后，后续调用降低 10–36%；
但剩余 138–156ms 是 embedding 服务端处理时间，客户端优化到不了。

**认知**：客户端优化的天花板由服务端延迟决定。

## 已知局限（新增）
- embedding 走远程 API，单次约 150ms，是首字延迟的主要来源
- 降到 10ms 级需要换本地模型（如 bge-small），时间成本高，暂不做
