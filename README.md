# AI 文档问答助手（RAG + Agent）

一个把本地文档变成可问答知识库的系统。
上传文档 → 语义检索 → 带引用出处的回答，支持多轮对话、流式输出与拒答。

> **这不是"调通 API 的 demo"。** 每一处优化都有对照实验和数据支撑，见下方「实验与结论」。

**在线体验**：https://ai-app-assistant-ctgmep4vbhvdahxthkjsnd.streamlit.app/
（Streamlit 免费实例会休眠，首次访问需等约 30 秒冷启动）

---

## 功能

- 📄 **文档入库**：PDF / Markdown / TXT → 分块 → 向量化 → 存入 Chroma；支持界面上传增量入库
- 🔍 **混合检索**：BM25 关键词 + 向量语义双路召回，RRF 排名融合
- 💬 **带引用回答**：每个结论标注 `[1] [2]`，附来源文件与块号
- 🛡️ **证据校验（拒答）**：生成前判断资料是否足够回答，不足则明确说"资料中未提及"，不硬编
- 🧠 **多轮对话**：会话隔离、三种上下文管理策略、代词查询改写
- 🧭 **意图路由**：区分知识问题 / 个人信息 / 闲聊，后两类跳过检索
- ⚡ **流式输出**：打字机效果，首字延迟可观测
- 📊 **成本可观测**：每次调用记录检索耗时、首字延迟、token（估算）

## 技术架构

```
用户输入
   ↓
意图路由（规则优先，认不出默认走知识路径）
   ├─ chitchat  → 直接生成（不检索）
   ├─ personal  → 读对话记忆（不检索）
   └─ knowledge ↓
                 查询改写（用历史把代词句补全）
                   ↓
             混合检索
              ├─ 向量检索（Top-10）→ Chroma
              └─ BM25 检索（Top-10）
                   ↓  RRF 排名融合 → Top-5
                证据校验（最高相似度 + 关键词覆盖率）
                   ↓ 不足 → 拒答
             上下文组装（检索结果 + 对话记忆）
                   ↓
             流式生成（带 [n] 引用）
                   ↓
             回答 + 来源 + 各项指标
```

**关键设计**：权限与数据边界、索引重建都放在链路之外（镜像无状态、索引可重建）；
业务链路上只做"路由 → 检索 → 校验 → 生成"四件事。

## 快速开始

```bash
git clone https://github.com/nicai99999/ai-qa-assistant.git
cd ai-qa-assistant
cp .env.example .env          # 仅首次需要；已有 .env 时不要执行（会覆盖真实 key）
uv sync
uv run python src/reindex.py  # 建索引（需先把 pdf/txt/md 放进 data/）
uv run streamlit run app.py   # 启动界面
```

> ⚠️ **`.env.example` 里全是占位符**（`your_deepseek_key_here` 这类）。
> **必须替换成真实 key**，否则调用会返回 `401 Unauthorized`。
>
> ⚠️ **`cp` 会覆盖已有文件。** 如果目录里已经有 `.env`（里面有真实 key），
> **不要执行上面那条 `cp`**，否则真实 key 会被占位符冲掉。只补缺的变量即可。
>
> ⚠️ 国内网络下 `uv sync` 可能超时，可临时加代理或换镜像源：
> ```bash
> # PowerShell
> $env:HTTPS_PROXY="http://127.0.0.1:10808"; uv sync
> # 或换清华源
> $env:UV_INDEX_URL="https://pypi.tuna.tsinghua.edu.cn/simple"; uv sync
> ```

> 仓库内的 PDF 未上传（体积原因），可自行把文档放进 `data/` 后执行上面的建索引命令。
> Docker：仓库提供 `Dockerfile` 与启动脚本，但**未在本地验证构建**（开发机未安装 Docker 环境）。

**运行测试**（全部离线，不调 API，约 3 秒）：

```bash
uv run pytest -q      # 43 passed
```

## 实验与结论

所有实验都在同一套 20 题评测集（16 题含可答/不可答标注）上完成，
口径为"命中块中包含 ≥2 个预期关键词"。

| # | 优化项 | 指标变化 | 结论 |
|---|---|---|---|
| 1 | **重分块**（70 字 → 400 字） | Top-1 **54.5% → 72.7%**<br>Top-K **90.9% → 100%** | 块过细导致语义割裂，是检索质量的主因 |
| 2 | **混合检索**（BM25 + 向量 + RRF） | Top-1 **72.7% → 81.8%** | 用「向量 K=10」对照组排除了"扩大候选池"的混淆，证明提升来自融合本身 |
| 3 | **上下文管理**（三种策略对比） | window ❌ / summary初版 ❌<br>summary改进 ✅ / priority ✅ | 摘要策略是"调参依赖型"；priority 在保留关键信息上更稳 |
| 4 | **查询改写** | 相似度 **+23 个百分点** | 但改写后三题全部命中同一高相似度陷阱块，**说明相似度不等于可答性** |
| 5 | **证据校验**（拒答） | 不可答识别率 **80%**<br>可答保留率 **100%** | 两个指标必须成对报：全拒答也能让识别率达到 100% |
| 6 | **流式输出** | 首字 **494 ms**（检索占 60%） | 定位到每次新建 embedding 客户端导致重复建连，改单例后降低 10–36% |
| 7 | **工具调用** | 工具选择 **6/6** | 发现并修复"工具返回逐块截断"导致答案被静默截掉的 bug |
| 8 | **意图路由** | 规则准确率 **83%** | 3 条难例暴露规则边界，是引入模型兜底的依据 |

### 三个最值得讲的数据

```
① 重分块：Top-1  54.5% → 72.7%
② 混合检索：Top-1 72.7% → 81.8%（有对照组，排除信息量混淆）
③ 证据校验：识别率 80% / 保留率 100%（成对报告）
```

### 一个反直觉的发现

在证据校验实验中，**一道不可答题的最高相似度（0.571）比 4 道可答题都高**：

```
0.571  「LangChain 的创始人是谁？」    不可答
────────────────────────────────────
0.537   块重合度设置过大会怎样          可答
0.480   复盘量化指标的数据来源要求       可答
0.477   接口地址配错的报错类型           可答
0.455   高频操作提取为技能包的商业价值    可答
```

**相似度衡量"像不像"，不衡量"能不能回答"。** 两者重叠，所以单阈值必然有漏网。

## 已知局限

1. **语料规模小**：88 块，BM25 的 IDF 统计不稳定，向量检索在 K=5 时已饱和
2. **相似度有漏网**：不可答最高分 0.571 会被单阈值放行（已是已知边界）
3. **token 为估算值**：流式接口拿不到精确 usage，按字符数估算，界面标注为估算
4. **检索走远程 embedding**：单次约 150 ms，是首字延迟的主要来源，降到毫秒级需换本地模型
5. **索引进版本库**：为让云端直接可用而提交了 `chroma_db`，生产环境应改为外部存储
6. **依赖 `.pth` / `PYTHONPATH`**：项目混用 `from xxx` 与 `from src.xxx` 两种 import 风格
